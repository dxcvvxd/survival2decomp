# Port patches

The Linux port of the game is carried here as patches against the *pristine*
decompile of the APK, so that "what did the port change" is always answerable and
the whole tree can be regenerated from an APK (`./compile.sh`).

## Layout

```
patches/
  base/                 required: makes the decompiled game compile and run on Linux
    removed-files.txt   decompiled files this stage deletes (Android-coupled code)
    patched-files.txt   files this stage modifies
    Engine/…/*.patch    one patch per modified file, mirroring the source path
    Survivalcraft/…/*.patch
  fixes/                optional: desktop behaviour changes on top of the 1:1 port
    patched-files.txt
    Survivalcraft/…
```

Rules:

* a patch file lives at `patches/<stage>/<source path>.patch`, e.g. the patch for
  `decompiled/src/Survivalcraft/Game/WebManager.cs` is
  `patches/fixes/Survivalcraft/Game/WebManager.cs.patch`
* paths inside a patch are always repo-root relative (`a/decompiled/src/...`), so
  they apply from the repo root with `patch -p1`
* `decompiled/` is generated by `./compile.sh` and is not tracked: the patch
  directories are the repository's only record of the port, and the paths above
  exist only while a tree produced from an APK is present
* a source file may be claimed by **exactly one** stage (`patched-files.txt`);
  `regen-patches.sh` refuses ambiguous setups because a second stage's diff would
  have to be generated against the first stage's output
* stages are applied in the order given to `./compile.sh` (`base` first; `fixes` on
  top), which is also the order they should be reasoned about in
* patches may carry a `#` comment header explaining *why*; the header survives
  regeneration

## Applying

```sh
./compile.sh <apk>                     # base only (1:1 with the APK's game code)
./compile.sh <apk> --fixes             # base + fixes
./compile.sh <apk> --stage <name>      # base + an extra stage
make fixes / make unfixes           # toggle the fixes stage in an existing tree
tools/patch-stages.sh apply|revert <stage>
```

File removals (`removed-files.txt`) are only performed by `./compile.sh` on a fresh
decompile; `tools/patch-stages.sh` only applies/reverts patch files, so a stage
applied that way must not contain deletions.

## Regenerating

```sh
tools/regen-patches.sh <apk>                  # refresh every stage's patches
tools/regen-patches.sh --stage base <apk>     # one stage
tools/regen-patches.sh --pristine-dir build/pristine/dec <anything>   # reuse a decompile
```

It diffs a pristine decompile against `decompiled/src` and rewrites the patches of
the stages it is told about, preserving each patch's comment header. For a stage
that is not currently applied to the tree (for example `fixes` while the tree is in
the 1:1 state) it leaves the existing patch untouched and says so. It then reports:

* changes in the tree that no `patched-files.txt` claims → decide which stage they
  belong to, add them, rerun
* files missing from the tree that no `removed-files.txt` lists → declare them as
  removals (or restore them)
* files present in the tree that the APK does not contain → a bug in the port

The full loop for changing game code is therefore:

```sh
./compile.sh <apk> --fixes     # get a patched tree to work in
$EDITOR decompiled/src/Survivalcraft/Game/Something.cs
tools/regen-patches.sh --stage fixes <apk>
make                        # rebuild
git diff patches/           # review the change as a patch
```
